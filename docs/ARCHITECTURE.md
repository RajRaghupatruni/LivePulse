# LivePulse Architecture

## M1 runtime path

```text
Deterministic simulator
  -> provider observation
  -> ingestion adapter / normalization
  -> PostgreSQL transaction (canonical_events + outbox_messages)
  -> outbox publisher (aiokafka producer)
  -> Redpanda: livepulse.events.football.v1
  -> projector consumer (aiokafka)
  -> PostgreSQL transaction (consumer_processed_events + match_state + pulse_timeline)
  -> in-process realtime notification
  -> /ws -> browser; REST APIs remain authoritative for resync
```

The simulator only supplies provider-shaped observations to the ordinary ingestion path. It never writes projections, timeline, WebSocket, or frontend state directly. API, outbox publisher, and projector run as supervised async tasks in the backend service for M1; they remain separate components with explicit boundaries so they can be split into processes later.

## Invariants

1. Provider DTOs do not leak into domain models or frontend contracts.
2. Canonical events are immutable.
3. Important discovered events are durable before publication is considered complete.
4. PostgreSQL and Redpanda are bridged by a transactional outbox.
5. Delivery is at-least-once; consumers are idempotent.
6. WebSocket messages may be missed; authoritative state is refetchable/resynchronizable.
7. Event history and current projections are separate concepts.
8. Redis, if added later, is not the only durable store for critical data.
9. Future AI is not authoritative state and has no arbitrary DB/code privileges.
10. Unified Pulse Timeline is core infrastructure/product functionality.

## Event identity and ordering

Events use UUIDv7 identifiers generated by the application (time-sortable, globally unique, supported without a custom ULID dependency). All timestamps are UTC. `dedupe_key` identifies an observation within its source; the database enforces uniqueness. `version` is a monotonically increasing per-match event version assigned while ingestion is serialized for the demo match. `schema_version` versions the canonical envelope independently of provider schemas. Events are append-only. A correction is a new event type/version in a later milestone.

The timeline uses a PostgreSQL-generated monotonic `BIGINT` sequence as a durable cursor. Cursor allocation is global and may contain gaps after transaction rollbacks; clients use it as an ordered resume watermark, not an assumption that every integer exists. The API reads its watermark before its page so a concurrent append can be replayed rather than skipped. Timeline order is ascending by cursor in storage and newest-first in the UI.

## Persistence and delivery

An ingestion transaction inserts both a canonical event and its outbox row. The outbox publisher claims rows with `FOR UPDATE SKIP LOCKED`, commits the claim briefly, publishes to Redpanda using `subject_id` as key, then marks the row published. A crash after broker acknowledgement and before marking causes duplicate publication, which is expected. Pending rows survive restarts. Events are retained in PostgreSQL as the durable history.

The projector transaction first claims event identity in `consumer_processed_events`, then applies the deterministic reducer and appends a user-visible timeline row. The transaction commits all changes together. Duplicate deliveries are ignored. Older/equal versions are recorded as processed but do not regress projection state. Delayed events for a previous demo match still update that match's own projection and history; the active-match pointer controls only which projection the live-state API returns. Reset removes canonical demo events before any old broker record can be applied. Realtime notifications are emitted only after commit. A process crash after commit but before notification is recovered by REST resynchronization and timeline cursor checks.

The demo's sequence assignment and reset/start coordination are serialized through database state and an in-process scenario lock. Reset deletes simulator-owned events and projections, preserves non-demo sources and the global timeline identity sequence, and signals connected browsers to refetch. M1 uses one backend instance in local Compose. Multi-instance simulator coordination is not claimed.

## Realtime and API

REST endpoints return current projection and timeline history. WebSocket notifications include cursor, event identity/type, UTC timestamp, and payload. A client can provide `last_cursor`; the server compares against durable timeline state and sends recoverable entries or an explicit `resync_required`. Heartbeats detect dead connections. Request IDs are accepted/generated and returned in error responses and structured logs.

## Operations and security boundaries

JSON logs carry service, request/correlation ID, event ID/type, consumer identity, and categorized errors where known. Health live means process responsiveness; health ready checks PostgreSQL and broker availability. M1 exposes a deterministic local demo; it is not hardened for public internet exposure. A security/threat model is required before external integrations or production. No secrets are committed. No Redis or Kubernetes is used.

## Planned instrumentation

Outbox, ingestion, consumer, projection, API, and WebSocket are explicit instrumentation boundaries for later OpenTelemetry/metrics/tracing. M1 does not claim distributed traces or production SLOs.
