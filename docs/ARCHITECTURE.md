# LivePulse Architecture

## M1 runtime path

```text
Deterministic simulator
  -> provider observation
  -> ingestion adapter / normalization
  -> PostgreSQL transaction (canonical_events + outbox_messages)
  -> outbox publisher (aiokafka producer)
  -> Redpanda: livepulse.events.football.v1
  -> projector consumer (aiokafka)
  -> PostgreSQL transaction (consumer_processed_events + match_state + pulse_timeline)
  -> in-process realtime notification
  -> /ws -> browser; REST APIs remain authoritative for resync
```

The simulator only supplies provider-shaped observations to the ordinary ingestion path. It never writes projections, timeline, WebSocket, or frontend state directly. API, outbox publisher, and projector run as supervised async tasks in the backend service for M1; they remain separate components with explicit boundaries so they can be split into processes later.

## Invariants

1. Provider DTOs do not leak into domain models or frontend contracts.
2. Canonical events are immutable.
3. Important discovered events are durable before publication is considered complete.
4. PostgreSQL and Redpanda are bridged by a transactional outbox.
5. Delivery is at-least-once; consumers are idempotent.
6. WebSocket messages may be missed; authoritative state is refetchable/resynchronizable.
7. Event history and current projections are separate concepts.
8. Redis, if added later, is not the only durable store for critical data.
9. Future AI is not authoritative state and has no arbitrary DB/code privileges.
10. Unified Pulse Timeline is core infrastructure/product functionality.

## Event identity and ordering

Events use UUIDv7 identifiers generated by the application (time-sortable, globally unique, supported without a custom ULID dependency). All timestamps are UTC. `dedupe_key` identifies an observation within its source; the database enforces uniqueness. `version` is a monotonically increasing per-match event version assigned while ingestion is serialized for the demo match. `schema_version` versions the canonical envelope independently of provider schemas. Events are append-only. A correction is a new event type/version in a later milestone.

The timeline uses a PostgreSQL-generated monotonic `BIGINT` sequence as a durable cursor. Cursor allocation is global and may contain gaps after transaction rollbacks; clients use it as an ordered resume watermark, not an assumption that every integer exists. The API reads its watermark before its page so a concurrent append can be replayed rather than skipped. Timeline order is ascending by cursor in storage and newest-first in the UI.

## Persistence and delivery

An ingestion transaction inserts both a canonical event and its outbox row. The outbox publisher claims rows with `FOR UPDATE SKIP LOCKED`, commits the claim briefly, publishes to Redpanda using `subject_id` as key, then marks the row published. A crash after broker acknowledgement and before marking causes duplicate publication, which is expected. Pending rows survive restarts. Events are retained in PostgreSQL as the durable history.

The projector transaction first claims event identity in `consumer_processed_events`, then applies the deterministic reducer and appends a user-visible timeline row. The transaction commits all changes together. Duplicate deliveries are ignored. Older/equal versions are recorded as processed but do not regress projection state. Delayed events for a previous demo match still update that match's own projection and history; the active-match pointer controls only which projection the live-state API returns. Reset removes canonical demo events before any old broker record can be applied. Realtime notifications are emitted only after commit. A process crash after commit but before notification is recovered by REST resynchronization and timeline cursor checks.

The demo's sequence assignment and reset/start coordination are serialized through database state and an in-process scenario lock. Reset deletes simulator-owned events and projections, preserves non-demo sources and the global timeline identity sequence, and signals connected browsers to refetch. M1 uses one backend instance in local Compose. Multi-instance simulator coordination is not claimed.

## Realtime and API

REST endpoints return current projection and timeline history. WebSocket notifications include cursor, event identity/type, UTC timestamp, and payload. A client can provide `last_cursor`; the server compares against durable timeline state and sends recoverable entries or an explicit `resync_required`. Heartbeats detect dead connections. Request IDs are accepted/generated and returned in error responses and structured logs.

The REST live-state/timeline response is the authoritative browser reconstruction. WebSocket frames are incremental notifications which may arrive after a REST snapshot, be duplicated, or be missed. The frontend merges only non-stale state versions, deduplicates timeline events by identity, and refetches REST state when the socket reports a gap or reconnects. It exposes `RECONNECTING` and `RESYNCING` while that recovery occurs; a visible last-known state is not treated as current until the snapshot is applied. Timeline cursor values are durable sequence watermarks, not event counts.

## Focus, Match Mode, and command surface

`app.domain.focus` owns deterministic attention semantics and returns a normalized `FocusState` with score, severity, reason, transient flag, expiry, source, subject, and Match Mode. A goal/red card raises attention for a bounded interval; on expiry the API derives attention again from the authoritative match lifecycle (live, halftime, scheduled, fulltime, or idle). The frontend displays this result and does not reimplement priority rules. Match Mode is a presentation of the same domain focus state, not a separate mutable UI guess. This keeps attention testable and reproducible and leaves AI outside authoritative state.

The persistent command bar has a small explicit frontend command registry for safe local actions (`run demo`, `reset demo`, `show system health`, `show match`, and `close`). These commands call the existing API or reveal existing product surfaces. Unmatched natural language is acknowledged as unavailable until the intelligence milestone; no backend command service or AI behavior is claimed. The message shape leaves room for later streamed assistant content/citations without adding unused execution capabilities now.

## System health

`GET /api/v1/system/health` reports normalized `healthy`, `degraded`, `unavailable`, or `unknown` states for components the local service can observe: a PostgreSQL query probe; a Redpanda broker metadata connection; successful outbox-poll and projector-poll heartbeats with freshness bounds; realtime client/overflow state; and demo-source activity. Probe details use safe codes, not connection strings or payloads. Overall status aggregates component states; process liveness and readiness endpoints retain their separate meanings. These observations cover this single local deployment only, not future external providers or multi-instance operations.

The response also has an extensible `providers` map, separate from infrastructure `components`, with normalized state (`healthy`, `degraded`, `unavailable`, `disconnected`, or `unknown`), configuration presence, safe detail code, last success/failure/observation, failure count, and rate-limit expiry. A complete credential/config set is not proof of connectivity: until a provider implementation makes an observation, it remains `unknown`; missing required config reports `disconnected`. Provider state does not alter infrastructure health aggregation. Secrets, tokens, message bodies, API payloads, and personal account/location values are excluded. This M3 contract has no external provider probes yet.

## Provider integration boundary (M3 foundation)

Provider packages live under `app.providers.<provider>`. Vendor DTOs and HTTP/OAuth details belong only in their provider package. The shared `Observation[ContentModel]` is immutable, UTC-stamped and typed; it carries provider/entity identity, provider version/checkpoint, and correlation ID. It is an intermediate observation, not a canonical event. Provider adapters own change detection and domain normalization, then emit the existing canonical event envelope into the unchanged PostgreSQL + outbox + Redpanda path. The M1 simulator remains on its existing normalization path.

Small structural capability protocols separate `PollSource`, `WebhookSource`, `CommandTarget`, and health reporting. Providers compose the capabilities they need; no `Provider.do_everything()` base class or marketplace exists. A shared OAuth protocol is intentionally deferred until Spotify and Google token flows are implemented and their reusable surface is evidenced. The registry is an in-process map for those explicit capabilities, not a dynamic plugin loader.

The single-instance poll scheduler owns bounded concurrency, per-poll timeout, jitter, exponential failure backoff, provider `Retry-After`, cadence hooks, observation handoff, cancellation, and health bookkeeping. It does not choose provider cadence or make scheduling distributed. Football can return its current scheduled/soon/live/halftime/fulltime interval through the cadence hook. GitHub webhooks remain a separate path; Gmail can persist checkpoints independently of poll scheduling. No provider scheduler is started unless concrete sources are registered.

`provider_connections` is the one shared per-provider connection record and `provider_checkpoints` stores provider/key-scoped opaque synchronization cursors. Sensitive credentials use a Fernet envelope with a local environment-supplied key. The SQLAlchemy credential column accepts only an `EncryptedCredentials` wrapper, rejecting plaintext assignments at persistence time. Decryption is an explicit server-side operation; no credential API or browser contract exists. Key rotation/re-encryption is a later operational requirement before long-lived production OAuth storage.

The backend command contract currently reserves `spotify.play`, `spotify.pause`, `spotify.next`, `spotify.previous`, `spotify.seek`, `spotify.volume`, and `spotify.transfer_device`. Arguments are command-specific and bounded; results carry a safe stable error code and optional state hint. M2's local demo/health/match commands remain in the frontend registry and are not moved into this provider command contract.

### Reserved event families

Provider event names are contracts, not implemented producers. Reserved families are: `football.match.{scheduled,kickoff,goal,score_corrected,yellow_card,red_card,substitution,halftime,second_half,fulltime}`; `spotify.playback.{started,paused,resumed}` plus `spotify.track.changed`, `spotify.device.changed`, and `spotify.context.changed`; `developer.workflow.{started,completed,failed}`, `developer.pull_request.{opened,merged}`, `developer.push.received`, and `developer.deployment.{completed,failed}`; `mail.message.received` and `mail.thread.updated`; `weather.conditions.updated`. Weather alerts are emitted only if the future source has an actual useful alert concept.

## Operations and security boundaries

JSON logs carry service, request/correlation ID, event ID/type, consumer identity, and categorized errors where known. Health live means process responsiveness; health ready checks PostgreSQL and broker availability. M1 exposes a deterministic local demo; it is not hardened for public internet exposure. A security/threat model is required before external integrations or production. No secrets are committed. No Redis or Kubernetes is used.

## Planned instrumentation

Outbox, ingestion, consumer, projection, API, and WebSocket are explicit instrumentation boundaries for later OpenTelemetry/metrics/tracing. M1 does not claim distributed traces or production SLOs.
