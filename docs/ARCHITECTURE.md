# LivePulse Architecture

## Runtime event paths

```text
Deterministic simulator or registered provider adapter
  -> provider observation
  -> ingestion adapter / normalization
  -> PostgreSQL transaction (canonical_events + outbox_messages)
  -> outbox publisher (aiokafka producer)
  -> Redpanda: livepulse.events.football.v1 (legacy topic name; M3 carries all canonical domains)
  -> projector consumer (aiokafka)
  -> PostgreSQL transaction (consumer_processed_events + domain projection + pulse_timeline)
  -> in-process realtime notification
  -> /ws -> browser; REST APIs remain authoritative for resync
```

The simulator only supplies provider-shaped observations to the ordinary ingestion path. Real providers normalize observations into immutable canonical events and persist those events with outbox rows. No source writes projections or timeline state directly. API, outbox publisher, projector, and the registered poll scheduler run as supervised async tasks in the backend; they remain separate components with explicit boundaries so they can be split into processes later.

## Runtime modes and network boundary

`LIVEPULSE_MODE` is an explicit typed setting with `PERSONAL_LOCAL` as the default and
`PUBLIC_DEMO` as the isolated portfolio mode. In PERSONAL_LOCAL the application is a
single-user, local-first service with no conventional account authentication. Its primary
trust boundary is loopback isolation: the development server binds `127.0.0.1`, Docker
publishes host ports only on `127.0.0.1`, and middleware accepts only loopback Host and
browser Origin values except for HTTP `POST /api/v1/webhooks/github` on an exact hostname
in `GITHUB_WEBHOOK_ALLOWED_HOSTS`. This exception does not apply to other paths, methods,
WebSockets, or Origin validation. CORS remains an exact localhost allowlist. Spotify and
Gmail OAuth callbacks continue to work on their configured loopback callback hosts.

PUBLIC_DEMO requires `PUBLIC_DEMO_DATABASE_URL`, an exact host allowlist, and an exact
HTTP(S) origin allowlist. The demo database name and login role must both differ from the
personal database values. The runtime engine and Alembic connect only to that dedicated
target and never fall back to `DATABASE_URL`. Provider credentials and weather coordinates
are discarded during settings validation; no real provider source, webhook, OAuth route,
provider API, or provider command is available in this mode. The deterministic fictional
match simulator is the only event source. The shipped demo Compose file also has its own
PostgreSQL volume and Redpanda service, and binds every host port to loopback. The mode is
reported by system health without exposing database URLs or provider configuration.

## Invariants

1. Provider DTOs do not leak into domain models or frontend contracts.
2. Canonical events are immutable.
3. Important discovered events are durable before publication is considered complete.
4. PostgreSQL and Redpanda are bridged by a transactional outbox.
5. Delivery is at-least-once; consumers are idempotent.
6. WebSocket messages may be missed; authoritative state is refetchable/resynchronizable.
7. Event history and current projections are separate concepts.
8. Redis, if added later, is not the only durable store for critical data.
9. Future AI is not authoritative state and has no arbitrary DB/code privileges.
10. Unified Pulse Timeline is core infrastructure/product functionality.

## Event identity and ordering

Events use UUIDv7 identifiers generated by the application (time-sortable, globally unique). All timestamps are UTC. `dedupe_key` identifies an observation within its source; the database enforces uniqueness. Football `version` is a monotonically increasing per-match event version. Non-football versioning and identity remain source/entity scoped as defined by their canonical adapters. `schema_version` versions the canonical envelope independently of provider schemas. Events are append-only. A correction is a new event type/version, never a mutation of history.

The timeline uses a PostgreSQL-generated monotonic `BIGINT` sequence as a durable cursor. Cursor allocation is global and may contain gaps after transaction rollbacks; clients use it as an ordered resume watermark, not an assumption that every integer exists. The API reads its watermark before its page so a concurrent append can be replayed rather than skipped. Durable append/replay order is cursor order. The frontend displays events by occurrence timestamp, newest first, with cursor as deterministic tie-break; a late-arriving football event therefore appears at its historical time without moving the replay cursor backward.

## Persistence and delivery

An ingestion transaction inserts both a canonical event and its outbox row. The outbox publisher claims rows with `FOR UPDATE SKIP LOCKED`, commits the claim briefly, publishes to Redpanda using `subject_id` as key, then marks the row published. A crash after broker acknowledgement and before marking causes duplicate publication, which is expected. Pending rows survive restarts. The default 365-day retention policy applies to ingested event history and timeline rows. Redpanda's canonical topic uses the same retention window. Retired-event tombstones keep only event UUID and a one-way hash of the dedupe key after payload deletion, so broker replay and provider retries remain idempotent without retaining event metadata. PostgreSQL cascades timeline, outbox, and processed-event rows with a retired canonical event; timeline cursor allocation is never reset.

The projector transaction first claims event identity in `consumer_processed_events`, then routes only `football.match.*` events through the football reducer. All other canonical event families use one generalized timeline-only path and never read or mutate football `match_state`. The transaction commits idempotency, any football state update, and the timeline row together. Duplicate deliveries are ignored. Older/equal football versions remain in history but do not regress current match state. Late post-fulltime football events are timeline-only unless they are explicit score corrections. Realtime notifications are emitted only after commit. A process crash after commit but before notification is recovered by REST resynchronization and timeline cursor checks.

The demo's sequence assignment and reset/start coordination are serialized through database state and an in-process scenario lock. Reset deletes simulator-owned events and projections, preserves non-demo sources and the global timeline identity sequence, and signals connected browsers to refetch. M1 uses one backend instance in local Compose. Multi-instance simulator coordination is not claimed.

## Realtime and API

REST endpoints return current projection and timeline history. WebSocket notifications include cursor, event identity/type, UTC timestamp, and payload. A client can provide `last_cursor`; the server compares against durable timeline state and sends recoverable entries or an explicit `resync_required`. Heartbeats detect dead connections. Request IDs are accepted/generated and returned in error responses and structured logs.

The REST live-state/timeline response is the authoritative browser reconstruction. WebSocket frames are incremental notifications which may arrive after a REST snapshot, be duplicated, or be missed. The frontend merges only non-stale state versions, deduplicates timeline events by identity, and refetches REST state when the socket reports a gap or reconnects. It exposes `RECONNECTING` and `RESYNCING` while that recovery occurs; a visible last-known state is not treated as current until the snapshot is applied. Timeline cursor values are durable sequence watermarks, not event counts.

The browser WebSocket 403 blocker was an Origin allowlist comparison bug: the middleware parsed the request Origin as `(scheme, host, port)` but compared the scheme string to the set of parsed tuples, rejecting allowed browser origins. It now compares the complete normalized tuple to the exact allowlist tuple. Tests cover an allowed development origin and rejected unlisted loopback ports/hosts for HTTP and WebSocket traffic; the allowlist was not loosened.

## Frontend platform boundary

The React UI depends on the shell-agnostic `web/src/lib/platform.ts` service for external launching, authorization entry, fullscreen/maximize requests, preference access, local API/WebSocket URL construction, backend lifecycle observations, and the in-app route seam. Browser behavior remains the fallback; feature components do not call native APIs or hard-code API hosts. Browser development uses same-origin Vite proxies, while the Tauri adapter supplies loopback endpoints `http://127.0.0.1:8000` and `ws://127.0.0.1:8000`. Tauri embeds the existing Vite production output; browser and desktop use the same React build and application behavior. The app opens external HTTP(S) links through Tauri's scoped opener plugin. No shell/process or filesystem capability is granted.

The UI checks `GET /health/ready` before considering the backend ready, then loads the existing System Health snapshot. Startup displays a restrained waiting screen; an unavailable backend exposes retry and bounded automatic recovery. After first readiness, a later outage keeps the dashboard mounted with last-known state while health/realtime indicators report degradation. API readiness and optional-provider health remain distinct. Tauri does not spawn or stop Docker/Compose services: Compose remains the local service owner, eliminating ambiguous shutdown ownership. In packaged Windows builds, the Tauri asset origin is exactly `http://tauri.localhost`; PERSONAL_LOCAL allows that one exact origin in addition to its existing loopback browser origins, while API Host validation remains loopback-only. PUBLIC_DEMO uses only its own configured allowlist and does not inherit the Tauri origin.

The Tauri v2 Rust host is deliberately small. It registers the URL opener and window-state plugins, sets a sensible resizable window size, and restores remembered geometry only when the previous monitor placement still intersects an available monitor. Its capability grants only the window fullscreen/maximize commands and HTTP(S) external URL opening; it does not grant arbitrary shell execution, filesystem access, or provider credentials. Standard Windows close behavior does not stop Compose, and backend/outbox/provider data remains durable. Full provider OAuth return into the packaged Tauri window is not part of this shell milestone; existing browser-mode OAuth flow and server-side encrypted tokens remain unchanged.

## Focus, Match Mode, and command surface

`app.domain.focus` owns deterministic attention semantics and returns a normalized `FocusState` with score, severity, reason, transient flag, expiry, source, subject, and Match Mode. A goal/red card raises attention for a bounded interval; on expiry the API derives attention again from the authoritative match lifecycle (live, halftime, scheduled, fulltime, or idle). The frontend displays this result and does not reimplement priority rules. Match Mode is a presentation of the same domain focus state, not a separate mutable UI guess. This keeps attention testable and reproducible and leaves AI outside authoritative state.

The home surface provides local navigation and a deterministic command palette for safe actions: open Home, Timeline, Focus, Settings, Gmail, the current match, next/previous match, local Focus presets, and configured external destinations. An unset Portfolio/Strata destination opens Settings. The palette has no natural-language/AI behavior, and the final UI does not expose M1 demo controls; simulator endpoints remain separate backend development/test paths.

## System health

`GET /api/v1/system/health` reports normalized `healthy`, `degraded`, `unavailable`, or `unknown` states for components the local service can observe: a PostgreSQL query probe; a Redpanda broker metadata connection; successful outbox-poll and projector-poll heartbeats with freshness bounds; realtime client/overflow state; and demo-source activity. Probe details use safe codes, not connection strings or payloads. Overall status aggregates component states; process liveness and readiness endpoints retain their separate meanings. These observations cover this single local deployment only, not future external providers or multi-instance operations.

The response also has a `providers` map, separate from infrastructure `components`, with normalized state such as `healthy`, `degraded`, `unavailable`, `disconnected`, `connecting`, `stale`, `rate_limited`, `auth_failure`, `provider_failure`, or `resyncing`, where runtime evidence supports it. It includes configuration presence, a safe detail code, last success/failure/observation, failure count, quota/cadence information where applicable, and rate-limit expiry. Missing required config reports disconnected; configured sources report connecting until observed. Health never claims a live connection from configuration alone. Provider state does not alter infrastructure health aggregation. Secrets, tokens, message bodies, provider payloads, and personal account/location values are excluded.

The health contract includes `runtime_mode`. In PUBLIC_DEMO every real provider reports
`disconnected`, `configured=false`, and `disabled_in_public_demo`, without reading provider
connection rows from a personal database.

## Provider integration boundary (M3)

Provider packages live under `app.providers.<provider>`. Vendor DTOs and HTTP/OAuth details belong only in their provider package. The shared `Observation[ContentModel]` is immutable, UTC-stamped and typed; it carries provider/entity identity, provider version/checkpoint, and correlation ID. It is an intermediate observation, not a canonical event. Provider adapters own change detection and domain normalization, then emit the existing canonical event envelope into the unchanged PostgreSQL + outbox + Redpanda path. The M1 simulator remains on its existing normalization path.

Small structural capability protocols separate `PollSource`, `WebhookSource`, `CommandTarget`, and health reporting, with shared checkpoint/credential services. Providers compose only the capabilities they need; there is no giant provider interface or marketplace. Spotify and Gmail keep distinct OAuth flows within their packages. The in-process registry registers football, GitHub reconciliation/webhook, Spotify, Gmail, and weather capabilities explicitly; it is not a dynamic plugin loader.

The single-instance poll scheduler owns bounded concurrency, per-poll timeout, jitter, exponential failure backoff, provider `Retry-After`, cadence hooks, observation handoff, cancellation, and health bookkeeping. Provider sources choose cadence. Football uses a quota-aware adaptive policy documented in `docs/providers/football.md`; GitHub webhooks remain a separate verified path. Gmail advances history checkpoints only with accepted canonical-event/outbox work. Source construction does not make external requests; registered poll tasks begin after application startup. Weather is registered even without a selected place so a user can choose one at runtime; it reports disconnected and performs no forecast request until a location exists.

Football's first successful fixture-ingestion transaction stores every observed fixture checkpoint and a provider-level `fixture-baseline:v1` marker. A successful empty fixture sync stores the same marker with zero fixtures, so a later arrival is recognized as a new fixture. Fixtures in a non-empty initial baseline do not emit `football.match.scheduled` merely because they were discovered. Later unseen fixtures and meaningful changes to known fixtures retain their normal event semantics; live facts observed during baseline discovery still use canonical persistence. On upgraded installations, existing fixture checkpoints count as an established baseline so the first newly appearing fixture is not suppressed. This uses the existing checkpoint schema and needs no migration.

`provider_connections` is the one shared per-provider connection record and `provider_checkpoints` stores provider/key-scoped opaque synchronization cursors. Sensitive credentials use a Fernet envelope with a local environment-supplied key. The SQLAlchemy credential column accepts only an `EncryptedCredentials` wrapper, rejecting plaintext assignments at persistence time. Decryption is an explicit server-side operation; no credential API or browser contract exists. Key rotation/re-encryption is a later operational requirement before long-lived production OAuth storage.

The backend command contract currently reserves `spotify.play`, `spotify.pause`, `spotify.next`, `spotify.previous`, `spotify.seek`, `spotify.volume`, and `spotify.transfer_device`. Arguments are command-specific and bounded; results carry a safe stable error code and optional state hint. M2's local demo/health/match commands remain in the frontend registry and are not moved into this provider command contract.

Weather location search uses Open-Meteo geocoding and returns only a normalized `WeatherLocation`. Selection and the five most recently used places are durable PostgreSQL records. The poll source reads the selected record for every observation, so a location change takes effect without restarting the process; the selection route requests one immediate poll through the existing scheduler. Per-location checkpoints prevent cross-city comparisons and suppress a timeline event merely for browsing to a new place. The browser receives physical place metadata from geocoding and never derives a city from its IANA timezone. Legacy environment coordinates are only a first-run bootstrap; resolving their display label uses a bounded one-time reverse-geocode request.

The dashboard clock remains system-local. The atmosphere alone uses the selected location's timezone-local time and the observed Open-Meteo condition category; absent location or conditions fall back to the neutral/system-time presentation rather than invented weather.

### Reserved event families

Implemented event families include `football.match.{scheduled,kickoff,goal,score_corrected,yellow_card,red_card,substitution,halftime,second_half,fulltime}`; `spotify.playback.{started,paused,resumed}` plus `spotify.track.changed`, `spotify.device.changed`, and `spotify.context.changed`; `developer.workflow.{started,completed,failed}`, `developer.pull_request.{opened,merged}`, `developer.push.received`, and `developer.deployment.{completed,failed}`; `mail.message.received` and `mail.thread.updated`; and `weather.conditions.updated`. Weather alerts are not synthesized because the selected source does not provide a useful alert concept.

## Retention and deletion

`RETENTION_DAYS` defaults to 365 (bounded from 30 to 3650 days). Retention is an explicit
deterministic maintenance command, not a background deletion loop. It removes only events
past the ingestion-time cutoff whose outbox is published and whose projector work is
durable. It preserves all events for an active/live match, each current match-state event,
pending publication/projection work, provider connection records, and all checkpoints needed
for incremental sync. Old inactive football state and its complete retired history can be
removed together. Retired identity tombstones retain only opaque identity/hash metadata.

The confirmation-gated personal purge removes canonical/timeline/outbox/idempotency history,
retired identities, match projections, the active-match pointer, and provider checkpoints;
it drops the mixed-domain Redpanda topic so event payloads are also removed. Encrypted
provider connection rows are removed only when the operator explicitly requests them. The
operator runs maintenance with API workers stopped to avoid racing live provider ingestion.
Schema and migration history are never deleted.

## Operations and security boundaries

JSON logs carry service, request/correlation ID, event ID/type, consumer identity, and categorized errors where known. Health live means process responsiveness; health ready checks PostgreSQL and broker availability. OAuth callback query material is stripped/redacted and `httpx` URL logging is disabled. The complete trust model and operational commands are recorded in `docs/SECURITY_AND_PRIVACY.md`. PERSONAL_LOCAL remains loopback-only except for the explicitly configured GitHub webhook POST host/path exception; PUBLIC_DEMO is limited to sanitized data in its isolated database and explicit host/origin allowlists. No secrets are committed. No Redis or Kubernetes is used.

## Planned instrumentation

Outbox, ingestion, consumer, projection, API, and WebSocket are explicit instrumentation boundaries for later OpenTelemetry/metrics/tracing. M1 does not claim distributed traces or production SLOs.
